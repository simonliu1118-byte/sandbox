# ScratchGame Project Rules

本檔只保存 ScratchGame 的固定專案規則；repository 共通版本、開發、CI 與 Local-first 規則依根 `REPOSITORY_RULES.md`。

## 1. 平台與發行

- 正式技術線：C# / .NET 8 / WPF。
- 目標平台：Windows x64。
- 正式發行以 self-contained portable folder 為目標，不要求使用者另外安裝 .NET。
- portable folder 至少包含 `ScratchGame.exe` 與彩券／UI／音效資源；Windows runtime/native libraries 可繼續封裝於 EXE，可替換美術不得強制嵌死在 EXE。
- Windows 視窗標題預設為「刮刮樂」。
- 主視窗只提供「固定預設尺寸」與「最大化」兩種正常使用狀態；禁止任意拖曳邊框改變視窗尺寸。最大化時內容等比例放大，還原時回固定預設尺寸。

## 2. 主畫面與操作

- 主畫面以彩券本體為視覺核心；彩券區保持「舞台背景 → 彩券 → 刮膜／互動／中獎效果」，不得在彩券背後堆疊無功能的面板框架。
- 彩券正式視覺以外部 PNG 美術資源為主，WPF 負責動態內容、刮除層、互動、文字與動畫。
- 沒有彩券時顯示「挑一張彩券」；結算後提供「再來一張」與「看看其他」。
- 挑選彩券預設顯示全部已啟用且有 Active 批次的彩券；面額只作為可選篩選條件，不得因預設篩選造成其他啟用彩券看似消失。
- 「全部刮開」會直接清除所有必要刮膜並自動完成兌獎。
- 每個刮獎區必須是獨立 ScratchSurface；例如九宮格就是 9 個互不干擾的刮膜區。
- 單一刮獎區達約 78%（可經實測微調）時，只標記該區已完成，不自動清除剩餘銀膜，使用者仍可繼續刮乾淨。
- 只有所有必要刮獎區都達完成門檻後，才執行自動判定與兌獎。
- 尚未開始刮獎時可「換一張」同款彩券；一旦開始刮獎即不可換票。

## 3. 使用者與未完成彩券

- 使用者檔案彼此獨立保存累計投入、累計兌獎、累計損益與遊玩歷史。
- 不做初始資金、補充資金或餘額不足限制；損益可為負值。
- 每個使用者最多同時存在一張 Pending Ticket。
- Pending Ticket 必須綁定建立它的使用者，且其獎項在發行當下即已決定。
- 正常關閉程式或切換使用者時，如果目前使用者尚有 Pending Ticket，必須先詢問；確認後直接揭曉同一張票並正常兌獎，不提供「放棄當作未中獎」。
- 若程式異常終止而留下 Pending Ticket，下次該使用者載入時不得重抽；直接揭曉原本既定彩券並完成兌獎。
- 使用者歷史至少保存日期時間、彩券、面額、批次與最終獎金。

## 4. 彩券定義

一張彩券定義固定包含：

- 名稱。
- 面額。
- 遊戲規則／版型。
- 總發行張數 `issueSize`。
- 每本張數 `ticketsPerBook`。
- 完整獎項表（各獎項固定張數）。
- 由獎項表自動計算的發行時中獎率。
- 所需美術、版面與音效設定。

規則：

- `issueSize > 0`、`ticketsPerBook > 0`，且 `issueSize % ticketsPerBook == 0`；總本數由程式計算。
- 彩券票號使用「款式編號-本號-本內序號」，各段至少 3 位補零，數量超過時自然增加位數，不截斷或循環。
- 彩券尚未建立任何批次前可修改或刪除。
- 彩券一旦建立第一批，核心定義即鎖定，不得修改面額、總發行量、每本張數、獎項張數或中獎率。
- 同一彩券的新批次必須使用相同固定獎項表；若要不同獎項機率／張數，建立新彩券。
- 已發行過的彩券不得真正刪除，只能停用；停用後不出現在新票選擇清單，但歷史仍可追溯。

## 5. 批次

- 每張彩券同時間只能有一個 Active 批次。
- 建立新批次會結束原 Active 批次；舊批次之後不可再抽票。
- 建立新批次前，舊批次不得存在未解決 Pending Ticket；如有，必須先直接揭曉並正常結算。
- 舊批次結束後不需永久保存完整可抽獎池；只保留必要歷史／統計資料。
- 批次售罄後不得自動建立下一批；由使用者手動決定是否發行新批次。

## 6. 有限票池與交易一致性

票池不是無限機率亂數。每個 Active 批次使用固定張數的有限獎項池。

1. 建立 Pending Ticket 時，從目前 Remaining／Available 數量依剩餘張數加權抽出獎項。
2. 在同一 SQLite transaction 內立即將該獎項 `Available - 1`，視為此票已正式發行；不再使用 Reservation 狀態。
3. Pending Ticket 保存該張已發行票的既定獎項與內容；正常兌獎只完成使用者獎金、歷史與 Pending 清除，不再次扣票池。
4. 「換一張」只允許尚未開始刮獎：同一 transaction 內先把舊票獎項放回 `Available + 1`，再抽新票 `Available - 1`；不得重複計入投入。
5. 異常終止後不得將 Pending 放回票池或重抽，必須結算原本那張。
6. 所有票池、使用者金額、Pending 與歷史變更必須使用 SQLite transaction 原子完成。
7. 舊資料庫中的 `reserved_count`／`reserved_*` 欄位可為 schema 向下相容而暫留，但正式業務邏輯不得再產生 Reservation；UI 亦不得顯示「保留中」。

## 7. 新票建立與投入

- 建立 Pending Ticket 時立即計入該使用者的投入金額（面額）。
- 程式異常恢復 Pending Ticket 時不得再次計入投入。
- 正常兌獎才計入兌獎金額。
- 最終個人損益 = 累計兌獎 - 累計投入。

## 8. Game Rule

- 主程式提供固定、公開的 `gameType` Rule Engine；ScratchPack 選用既有 gameType 與合法參數，不攜帶任意玩法程式碼。
- 已發布 gameType 的核心勝負判定語意不得修改；未來變體新增新的 gameType（例如 `1-2`），不改舊規則。
- GameType 1 為「星星連線」：`gridSize=3/4/5` 分別要求完整 3/4/5 顆星成線；只計完整橫列、完整直列及兩條完整大對角線，不計短斜線或局部連線。
- GameType 1 可新增不改變核心判定的 optional 生成／呈現參數；舊包缺少新參數時必須採保持舊行為的預設值。`allowNearMissStars` 預設 `false`。
- Prize Tier 本身保持「金額＋張數」；各玩法引擎負責將金額映射到其合法 outcome。

## 9. ScratchPack 與資源

- 外部彩券包副檔名為 `.scratchpack`。
- 唯一正式格式規格為 `SCRATCHPACK_SPEC.md`；規格必須足以讓不同 AI 或第三方在沒有本對話的情況下製作相容彩券包。
- ScratchPack 只允許資料、美術與音效，不允許攜帶或執行任意程式碼、DLL、EXE 或 script。
- `canvas` 只能選擇主程式公開的固定尺寸代碼；既有代碼語意永不改變。
- `priceDisplay=0` 代表底圖自帶完整面額；`priceDisplay=1` 代表主程式於該 Canvas 的標準位置繪製完整面額徽章（外框、底色、金額）。
- 彩券包可提供自訂銀膜；未提供時使用主程式預設銀膜。刮膜形狀只可使用該版 Developer Guide 公開支援的 Shape。

## 10. 資料與備份

- 正式資料使用 SQLite，預設位於 `%LOCALAPPDATA%\ScratchGame\scratchgame.db`，與 EXE 分離以確保更新程式不會刪除使用者資料。
- 一般自動備份：程式啟動時檢查，距最近成功備份達 3 天才建立新備份。
- 備份最多保留最近 5 份，超過即刪除最舊一份。
- 資料庫 schema migration 前無論距離上次備份多久，都必須先建立安全備份；完成後仍以最多 5 份輪替。
- 使用者執行資料與備份不得提交至 Git。
